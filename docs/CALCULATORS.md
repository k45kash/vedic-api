# Логика калькуляторов — подробное описание

Источник: `nakshatry_polnyy (14).html` (сборка коллеги). Логика перенесена 1:1 в
TypeScript-модули `calculators/`, данные — в `data/*.json`. Здесь описано, **как
именно считается каждый калькулятор**: алгоритм, веса, стоп-факторы, пороги.

Все входы в TS-версии — единообразные номера: накшатры **1..27**, знаки **1..12**
(Овен = 1), дома **1..12**, титхи **1..15 + пакша**. В исходном HTML накшатры были
0-индексными — при сверке с оригиналом учитывайте сдвиг на единицу.

---

## 1. Тара-бала (`tara.ts`)

Личная благоприятность дня: сравнение **Джанма-накшатры** (накшатра натальной
Луны) с **накшатрой дня** (транзитная Луна — из `/api/calendar`).

### Алгоритм

```
diff  = ((dayNo − janmaNo) mod 27 + 27) mod 27     // 0..26
pos   = diff + 1                                    // позиция дня от Джанмы, 1..27
tara  = diff mod 9                                  // индекс тары, 0..8
group = pos ≤ 9 → 1 (Джанмаркша) | pos ≤ 18 → 2 (Кармаркша) | 3 (Адханаркша)
```

### Девять тар

| № | Тара | Качество |
|---|------|----------|
| 1 | Джанма | смешанная (нейтральная) |
| 2 | Сампат | благоприятная (очень) |
| 3 | Випат | **неблагоприятная** |
| 4 | Кшема | благоприятная |
| 5 | Пратьяри | **неблагоприятная** |
| 6 | Садхака | благоприятная |
| 7 | Вадха/Наидхана | **неблагоприятная** (самая тяжёлая) |
| 8 | Митра | благоприятная |
| 9 | Ати-митра | благоприятная |

### Сила неблагоприятных тар по группам (метод школы)

Негативная тара (3, 5, 7) ослабевает от круга к кругу:

- **Группа 1** (позиции 1–9): `strength = 'full'` — действует весь день (24 ч);
- **Группа 2** (10–18): `strength = 'partial'` — только часть суток (~8 ч):
  12-я позиция (Випат) — первые ~8 ч, 14-я (Пратьяри) — последние ~8 ч,
  16-я (Наидхана) — средние ~8 ч;
- **Группа 3** (19–27): `strength = 'mild'` — почти нейтральна, **кроме** случая,
  когда управитель накшатры в падении или под плохим аспектом (это условие в
  расчёте не автоматизировано — предупреждение для астролога).

### Особое правило школы

`schoolAvoid = (pos === 27)` — 27-ю накшатру от Джанмы школа рекомендует избегать,
даже если тара формально благоприятна (Парама-митра). В первоисточниках
«разрушительной» (Вайнашика) называют то 22-ю, то 23-ю — до сверки в коде
оставлена только 27-я (так было и в HTML).

### Навата́ра-чакра (`taraChakra`)

Таблица всех 27 накшатр от заданной Джанмы: позиция, тара, качество, управитель
накшатры (цикл Вимшоттари: Кету–Венера–Солнце–Луна–Марс–Раху–Юпитер–Сатурн–Меркурий),
традиционное пожертвование-упайя по таре (`tara_dana.json`). Рендерится сеткой
9 строк × 3 группы.

**Мнемоника**: последовательность тар совпадает с последовательностью управителей
Вимшоттари, поэтому тару дня можно определить по управителю накшатры дня, зная
управителя своей Джанмы.

**Интеграция с API**: janmaNo — из `/api/horoscope` → `nk.num`; накшатра дня — из
`/api/calendar` (транзит Луны на дату).

## 2. Ашта-кута — совместимость пары (`kuta.ts`)

Классическая система 36 баллов из 8 кут. **Реализованы 4 куты (21 балл)** — те,
что считаются по одним накшатрам Луны. Остальные 4 (Варна — 1, Вашья — 2,
Граха-майтри — 5, Бхакут — 7) требуют раши Луны обоих партнёров; API отдаёт знак
Луны (`planets[Луна].sign_num`), так что их можно добавить следующим шагом.

### Гана-кута (макс 6)

По полю `gana` накшатры (Дэва / Манушья / Ракшаса):

| Сочетание | Балл |
|---|---|
| одна гана | 6 |
| Дэва + Манушья | 5 |
| Манушья + Ракшаса | 1 |
| Дэва + Ракшаса | 0 |

> Исправление относительно HTML: в данных гана записана неоднородно («Дэва» и
> «Дэва (божественная)»), из-за чего оригинальный код для части пар не
> распознавал сочетание и молча ставил 6. В TS-версии значение нормализуется до
> первого слова — считаются все пары.

### Йони-кута (макс 4) — упрощённая

По животному йони (`yoni`) и его врагу (`yoni_enemy`):

- одинаковое животное — **4**;
- йони одного — враг йони другого (в любую сторону) — **0**;
- иначе — **2** (нейтрально).

Полная классическая матрица 14×14 (друг/нейтрал/враг) не реализована — только
три уровня. Это осознанное упрощение исходника.

### Тара-кута (макс 3)

Тара считается **в обе стороны** (от невесты к жениху и обратно): каждая
не-неблагоприятная тара даёт 1,5 балла. Обе хорошие — 3, одна — 1,5, обе плохие — 0.

### Нади-кута (макс 8)

Нади (Ади / Мадхья / Антья) извлекается из текстового поля `compat` накшатры
регуляркой `Нади\s*[—-]\s*([А-Яа-я/]+)` (работает для всех 27). Разные нади — **8**;
одинаковые — **0 + флаг `nadiDosha`** (нади-доша — традиционно серьёзное
препятствие для брака, важнее потерянных баллов).

### Интерпретация итога

Частичный максимум — 21. Полный порог для брака традиционно — **от 18/36** при
отсутствии нади-доши. В UI обязательно показывать, что расчёт частичный.

## 3. Подбор события — мухурта (`event-picker.ts`)

Весовая модель: насколько конкретный день подходит конкретному делу. 33 события
в `events_muhurta.json`, у каждого — списки благоприятных/избегаемых накшатр,
дней недели, титхи, йог.

### Веса факторов (`picker_weights.json`)

| Фактор | Вес | Комментарий |
|---|---|---|
| Тара-бала | 4 | главный личный фактор (практика школы) |
| Накшатра дня | 3 | главный фактор соответствия делу |
| Титхи | 2 | |
| День недели | 2 | |
| Йога | 1 | только бонус, отсутствие в списке не штрафует |

Каждый **заполненный** вход добавляет свой вес в знаменатель `total`; совпадение
со списком благоприятного даёт `+вес`, с избегаемым — `−вес`, нейтрально — 0.

```
pct = round(max(0, gained) / total × 100), затем pct = min(pct, vetoCap)
```

### Стоп-факторы (vetoCap — потолок оценки)

Вето не просто вычитает баллы — оно **ограничивает итог сверху**, чтобы хорошие
остальные факторы не «перекрыли» жёсткое противопоказание:

| Стоп-фактор | Потолок | Для каких событий |
|---|---|---|
| Накшатра дня в списке избегаемых | 40 % | все |
| Рикта-титхи (4, 9, 14 — «пустые руки») | 30 % | начинания: свадьба, новоселье, бизнес, обучение, имянаречение, зачатие, договоры |
| Амавасья (15-я титхи Кришна-пакши) | 20 % | мирские дела: + путешествия, транспорт, строительство, финансы |

Сопоставление накшатр со списками — по вхождению подстроки в обе стороны
(в данных встречаются краткие/полные написания).

### Вердикты

≥ 75 % — «Отличное окно» · ≥ 55 % — «Хорошее окно» · ≥ 40 % — «Приемлемо, с
компромиссом» · < 40 % — «Слабое окно».

### Интеграция с API

Это ключевой сервисный сценарий: **прогнать диапазон дат** через `scoreEvent` и
показать лучшие окна. Из `/api/calendar` — накшатра дня, из `/api/panchang` —
титхи (сквозной номер 1..30 → `splitTithi()` → 1..15 + пакша), день недели — из
даты (`weekdayRu`). Йога дня в API пока не считается — поле опционально.

## 4. Садхана — день изготовления изделия (`sadhana.ts`)

Выбор дня работы с металлом планеты (4 металла в `sadhana.json`: медь—Марс,
серебро—Луна, железо—Сатурн, свинец—Раху; у каждого — стихия, основной день,
резервные дни по дружбе планет, этапы работ).

### Принцип: стоп-факторы исключают день полностью

В отличие от подбора события (где вето — потолок), здесь любой стоп-фактор даёт
статус **excluded**: выбор должен идти только из хороших дней.

Стоп-факторы:

- день недели не является ни основным, ни резервным для металла;
- тара 1 (Джанма — спорная), 3 (Випат), 5 (Пратьяри), 7 (Наидхана);
- 27-я накшатра от Джанмы (правило школы);
- рикта-титхи (4, 9, 14);
- Амавасья (15-я Кришна-пакши).

### База по дню недели

| День | Основное действие | Доработки (`isFinishing`) |
|---|---|---|
| Основной день металла | 100 | 100 |
| Резервный (полноценный) | 75 | 90 |
| Крайний резерв (в note есть «крайн») | 55 | 80 |

Резерв распознаётся по `sadhana.json → metals[].reserve[]`; «крайность» — по
подстроке «крайн» в note. Смысл раздельной оценки: основное действие стараются
делать строго в день планеты, доработки допускают резерв.

### Бонусы

- благоприятная тара (2, 4, 6, 8, 9) — плюс;
- хорошие титхи (2, 3, 5, 7, 10, 11, 13, Пурнима) — плюс.

Формула процента (потолок 100):

```
база 100:  pct = min(100, 90 + плюсов×5)   // без плюсов основной день = 90
база ≥ 90: pct = min(100, база + плюсов×3)
иначе:     pct = min(100, база + min(плюсов×8, 18))
```

Вердикты: ≥ 90 «Отлично» · ≥ 75 «Очень хорошо» · ≥ 60 «Хорошо» · иначе «Приемлемо».

UI сценария — два дня: «День 1 · основное действие» и «День 2 · доработки»
(второй считается с `isFinishing: true`).

## 5. Карта «дома и знаки» (`chart.ts`)

Раскладка планет по домам системой **Whole Sign** (целознаковые дома — так же
считает и API):

```
дом знака:  houseForSign(lagna, sign) = ((sign − lagna + 12) mod 12) + 1
знак дома:  signForHouse(lagna, house) = ((lagna − 1 + house − 1) mod 12) + 1
```

### Достоинство планеты в знаке (`dignity`)

По `signs.json`: `exalt` (строка вида «Солнце (10°)») — экзальтация, `debil` —
падение, `ruler` — свой знак; поиск по вхождению имени планеты. Градус
экзальтации не проверяется (в HTML тоже не проверялся) — достоинство по знаку.

### Сборка трактовки (`analyzeChart`)

Для каждой планеты: дом → текст из `placements.json → houses[slug][house−1]`,
знак → `placements.json → signs[slug][sign−1]` (slug: Солнце=surya, Луна=chandra,
Марс=mangala, Меркурий=budha, Юпитер=guru, Венера=shukra, Сатурн=shani, rahu, ketu),
плюс справка дома (`houses.json`) и знака (`signs.json`), достоинство, ретро-флаг.
Порядок вывода — традиционный: Солнце → Кету.

**Интеграция с API**: `chartFromHoroscope()` берёт `lagna.sign_num` и
`planets[].sign_num` из `/api/horoscope` — ручной ввод планет из HTML больше
не нужен. Ретро-флага в API пока нет (поле опционально).

В HTML вокруг этого была ещё отрисовка SVG-карт (северный/южный стиль) — это
чисто презентационный слой, его в Nuxt удобнее делать Vue-компонентом
(референс: `chartSVGNorth`/`chartSVGSouth` в исходнике; готовый компонент
`LagnaChart.vue` уже есть в frontend-nuxt).

## 6. Накшатра по долготе (`nakshatra.ts`)

```
идx = floor(долгота / 13°20′) mod 27; пада = floor(остаток / 3°20′) + 1
```

Вход — **сидерическая** долгота (аянамша уже вычтена; API отдаёт `sid`).
Дублирует `get_nk` из Python-API — нужен для клиентских сценариев (например,
интерактивный круг пад) без похода на сервер. Там же: управитель по циклу
Вимшоттари, ярлыки для селектов, список гандантовых накшатр (1, 9, 10, 18,
19, 27 — стыки вода→огонь).

## 7. Адаптеры API (`api-adapter.ts`)

| Функция | Что делает |
|---|---|
| `janmaFromHoroscope` | `/api/horoscope` → номер Джанма-накшатры (`nk.num`) |
| `chartFromHoroscope` | `/api/horoscope` → `{lagnaSign, planets[]}` для `analyzeChart` |
| `splitTithi` | сквозной номер титхи 1..30 (как в `/api/panchang`) → `{tithi: 1..15, paksha}`; 30 = Амавасья → 15/krishna |
| `weekdayRu` | `Date` → русское название дня недели (ключи данных — русские) |

## Что НЕ переносилось (и почему)

- **SVG-отрисовка карт и круга пад** — презентация, а не логика; в Nuxt это
  Vue-компоненты. Вся расчётная часть (маппинги дом↔знак, данные пад с градусами
  в `padas.json`) перенесена.
- **Просмотрщики справочников** (истории планет, панчанга, мантры, глоссарий,
  ретроградность, 30 мухурт, аспекты/даши) — там нет вычислений, только рендер
  `data/*.json`; в Nuxt это страницы над готовыми JSON.
- **Тултипы терминов, поиск/фильтры сетки** — UI-механика.

## Оговорки достоверности (из исходника, важно сохранить в UI)

Автор базы явно помечал: веса подбора события — оценочная модель школы; йони-кута
упрощена; ашта-кута частичный; толкования «планета в накшатре» — рабочая версия;
правило 27-й накшатры требует сверки с первоисточниками (22-я/23-я в разных
традициях). Эти дисклеймеры стоит выводить рядом с результатами.
