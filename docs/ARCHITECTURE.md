# Архитектура

Документ описывает, из чего состоит сервис, как части связаны и почему приняты
ключевые решения. Текущие задачи — в [`PLAN.md`](PLAN.md).

---

## 1. Общая схема

```
┌──────────────────────┐        HTTPS/JSON        ┌────────────────────────┐
│  Frontend (Nuxt 3)   │ ───────────────────────► │   Backend (FastAPI)    │
│  статичная SPA       │ ◄─────────────────────── │   Python 3.11          │
│  Railway: front      │      JWT в заголовке     │   Railway: vedic-api   │
└──────────────────────┘                          └───────────┬────────────┘
                                                              │
                                            ┌─────────────────┴─────────────────┐
                                            │                                   │
                                   ┌────────▼────────┐                ┌─────────▼────────┐
                                   │ Swiss Ephemeris │                │    MongoDB       │
                                   │ ephe/ (DE431)   │                │ пользователи,    │
                                   │ файлы на диске  │                │ тарифы, роли     │
                                   └─────────────────┘                └──────────────────┘
```

Два независимых сервиса на Railway из одного репозитория. Фронтенд — статика,
никакого SSR: он общается с API только через браузер пользователя.

## 2. Backend

### Расчётное ядро

Четыре независимых модуля, каждый — чистая функция «входные данные → результат»,
без состояния и без обращений к БД:

| Модуль | Точка входа | Что считает |
|--------|-------------|-------------|
| `Panchangam.py` | `calc_panchang()` | титхи, мухурты, хоры, восход/закат |
| `nakshatra_calculator.py` | `calculate()` | накшатра Луны, лагна, планеты по домам |
| `nakshatra_calendar.py` | `calc_calendar()` | транзиты Луны по накшатрам и падам |
| `sade_sati.py` | `calc_sade_sati()` | циклы Сатурна: Сади Сати, Аштама, Кантака |

Общее вынесено в `utils.py` (таблица `NAKSHATRAS`, `dms_sign`, `dt_to_jd`).

**Принцип точности.** Все расчёты идут через Swiss Ephemeris (файлы DE431 в `ephe/`),
аянамша — Лахири (`SIDM_LAHIRI`). Приближённые методы (Moshier, Meeus) и фолбэки
намеренно удалены: лучше явная ошибка, чем тихо неточный результат. Для Луны у
границы знака применяется топоцентрическая поправка — она способна изменить знак,
и об этом сообщается в ответе.

### Слой API

`main.py` — тонкая обёртка: валидация входа через Pydantic-модели, вызов
расчётной функции, обработка ошибок. Бизнес-логики в нём нет.

```
main.py
 ├── lifespan          → инициализация MongoDB (толерантно к отказу)
 ├── CORS middleware   → allow_origins=["*"] (см. «Открытые вопросы»)
 ├── auth_router       → /auth/*, /users/*
 └── публичные роуты   → /api/*
```

## 3. Frontend

Nuxt 3 в режиме **SPA** (`ssr: false`), собирается в статику (`nuxt generate`)
и раздаётся пакетом `serve`. Сервера Node в проде нет — только отдача файлов.

```
pages/          index (накшатра) · panchang · calendar · sade-sati
components/     BirthForm · CityField (поиск города + авто-TZ) · LagnaChart
composables/    useApi (обёртка fetch) · useBirthForm (общее состояние формы)
layouts/        default.vue — навигация, глобальные стили
```

Адрес API задан в `nuxt.config.ts` (`runtimeConfig.public.apiUrl`). Так как сборка
статическая, **значение вшивается на этапе build** — менять его нужно до сборки,
а не в рантайме.

`CityField` дополнительно ходит в Nominatim (OpenStreetMap) за координатами города
и в наш `/api/tz` — за историческим часовым поясом (учитывает декретное время,
отмену перевода часов в 2011 и т.п.).

## 4. Авторизация

> Фундамент готов; соц-провайдеры и защита роутов — в работе, см. `PLAN.md`.

### Выбор подхода

**Self-hosted** (`fastapi-users` + MongoDB), а не внешний провайдер вроде Clerk
или Supabase. Причина простая: приоритетные способы входа — **VK, Telegram,
Yandex**, а managed-решения их либо не поддерживают, либо поддерживают плохо.

### Компоненты

```
auth/config.py    настройки из окружения (pydantic-settings)
auth/db.py        AsyncMongoClient + init_beanie
auth/models.py    User: email, plan, role, oauth_accounts
auth/users.py     UserManager, JWT-стратегия, зависимости доступа
auth/router.py    сборка роутов; сюда же подключаются провайдеры
```

Стек: `fastapi-users[beanie]` + Beanie 2.0. Beanie 2.0 отказался от `motor`
в пользу нативного `pymongo.AsyncMongoClient` — драйвер именно такой.

### Поток токенов

Фронтенд — статичная SPA, поэтому серверных сессий нет: используется
**JWT в заголовке** `Authorization: Bearer <token>`. Все способы входа
(пароль, VK, Yandex, Telegram) в итоге сходятся к одному пользователю в Mongo
и выдают **один и тот же токен приложения** — источник входа для остального
кода не важен.

### Провайдеры: два разных механизма

| Провайдер | Механизм | Реализация |
|-----------|----------|-----------|
| Yandex, Google | OAuth2 | встроенные клиенты `httpx-oauth` |
| VK (VK ID) | OAuth2 | свой клиент — наследник `BaseOAuth2` |
| **Telegram** | **не OAuth2** | Login Widget + проверка подписи HMAC-SHA256 по токену бота |

Telegram — отдельный случай: у него нет redirect-потока. Виджет отдаёт
подписанные данные, бэкенд проверяет подпись, находит или создаёт пользователя
и выдаёт обычный JWT приложения.

### Уровни доступа

На модели `User` два поля:

- `plan` — тариф (`free`, `premium`, …)
- `role` — роль (`user`, `admin`)

Готова зависимость `require_plan("premium")` для защиты эндпоинтов. **Пока она
нигде не навешана** — все расчёты публичны, чтобы не мешать разработке прототипа.
Закрывать функционал будем точечно, когда состав фич устаканится.

Изменить свой `plan`/`role` через `PATCH /users/me` **нельзя** — эти поля
намеренно исключены из схемы `UserUpdate`, иначе любой пользователь поднял бы
себе тариф сам.

### Отказоустойчивость

Подключение к Mongo в `lifespan` обёрнуто в `try/except`: если база недоступна,
приложение стартует, пишет предупреждение и работает **без авторизации**.
Публичные расчёты при этом не страдают. Это позволяет катить бэкенд на Railway
до того, как база поднята.

## 5. Хранение данных

MongoDB как отдельный сервис на Railway.

> **Обязательно:** к сервису Mongo должен быть прикреплён **Volume с точкой
> монтирования `/data/db`**. Контейнеры Railway эфемерны — без вольюма база
> будет стираться при каждом редеплое.

Коллекция `users` (создаётся автоматически, индекс по email — из `fastapi-users`).
Расчётные модули к базе не обращаются вообще: они остаются чистыми функциями.

Строку подключения приложение берёт из `MONGODB_URI` **или** `MONGO_URL` —
второе имя Railway задаёт сам, поэтому на проде переменную прописывать не нужно.

Секреты (строка подключения, `JWT_SECRET`, ключи провайдеров) — только через
переменные окружения. Локально — файл `.env`, он в `.gitignore`;
в репозитории лежит лишь шаблон `.env.example`.

## 6. Деплой

Оба сервиса собираются на Railway через **nixpacks** из одного репозитория,
различаются Root Directory:

| Сервис | Root | Сборка | Запуск |
|--------|------|--------|--------|
| `vedic-api` | `/` | `pip install -r requirements.txt` | `uvicorn main:app --host 0.0.0.0 --port $PORT` |
| `vedic-nuxt-front` | `frontend-nuxt/` | `npm install && npm run build` | `serve .output/public -l $PORT` |

Версия Node на фронте определяется автоматически из `engines` в `package.json`
(`>=22.12.0` → Railway ставит 22.x). Это важно: Vite 7 не работает на Node ниже 22.12.

## 7. Принятые решения

| Решение | Причина |
|---------|---------|
| Только Swiss Ephemeris, без фолбэков | точность важнее доступности; неверный результат хуже ошибки |
| Nuxt 3 вместо Astro | единый фронтенд; Astro-версия удалена, чтобы не поддерживать два UI |
| SPA (`ssr: false`) | расчёты идут в браузере пользователя, SSR не даёт выгоды |
| Self-hosted auth | managed-провайдеры не покрывают VK / Telegram / Yandex |
| JWT, а не сессии | фронтенд — статика, серверного состояния нет |
| Расчёты не трогают БД | ядро остаётся чистым и тестируемым независимо от auth |

## 8. Открытые вопросы

- **CORS** сейчас `allow_origins=["*"]` — удобно в разработке, но перед запуском
  авторизации стоит сузить до домена фронтенда.
- **Отправка писем** — роуты подтверждения email и сброса пароля существуют,
  но реального SMTP пока нет: письма никуда не уходят.
- **Тарифы и биллинг** — модель `plan` заложена, но платежи не проектировались.
- **Тесты** — автоматических тестов пока нет.
